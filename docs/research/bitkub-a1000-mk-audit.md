# Bitkub `A1000-MK` request audit

Checked on 2026-09-01 against Bitkub's official documentation repository and
its public issue tracker. This is an investigation record, not an assertion
about Bitkub's internal meaning for the legacy `A1000-MK` code.

## Result

Issue [#138](https://github.com/bitkub/bitkub-official-api-docs/issues/138)
does **not** apply to Moondi's failing balance request.

That issue concerned the now-removed `POST /api/v3/market/balances` endpoint.
The reporter was sending the literal body string `{}` and later wrote that
passing `undefined` as Axios's second `post` argument omitted the body and
solved their invalid-signature problem. The comment is a report from the issue
author, not an official Bitkub staff response. It is nevertheless useful for
the narrow Axios/POST case it describes.

Moondi instead calls the current `GET /api/v4/wallet/balances` endpoint, which
the current V4 reference defines with no body. The V3 `/api/v3/market/balances`
endpoint discussed in #138 was removed on 2026-05-26; Bitkub's current
announcement names the V4 wallet endpoint as its replacement. Therefore,
adding an `undefined` body, `{}`, or any POST payload to Moondi would be an
incorrect change and could only make the signed request differ from the
documented GET request.

## Moondi implementation audit

The balance path is implemented in
[`packages/exchanges/src/bitkub/index.ts`](../../packages/exchanges/src/bitkub/index.ts):

1. `fetchBalances()` calls `secureGet('/api/v4/wallet/balances')`.
2. `secureGetRaw()` fetches a new V3 server timestamp.
3. It constructs `requestPath` once as `path + encodedQuery` and uses that
   exact string both in the HMAC input and the outgoing URL.
4. With the default empty query, the signed material is exactly
   `<timestamp>GET/api/v4/wallet/balances`.
5. The outgoing request has no body and no explicit `method`; Fetch defaults
   it to `GET`. It includes the documented auth headers and uses `cache:
   'no-store'`.

This matches the documented V4 endpoint and signing construction. In
particular, there is no Axios call and no POST-body serialization path involved
in `fetchBalances()`.

For other Moondi GET requests with query parameters, the implementation also
uses the same `URLSearchParams` serialization for the signature and final URL.
That is the required invariant. If a caller later supplies the optional wallet
`segment`, its encoded query must remain in both places, e.g.
`<timestamp>GET/api/v4/wallet/balances?segment=funding`.

## Supported next diagnostic

No code change is justified by issue #138. The meaningful comparison is one
live GET request generated by the same signing implementation in each network
environment, with only non-secret metadata recorded: HTTP status, Bitkub error
code/message, timestamp age at send time, and a hash/fingerprint of the
canonical signed material. Never log the API key, secret, HMAC signature, or
wallet response.

The existing Bruno evidence already confirms that the documented `GET` request
and the same credential pair work outside the Worker. If the Worker continues
to return the undocumented legacy `A1000-MK` result after this audit, Bitkub is
the authoritative party to interpret that code or diagnose any network/account
policy attached to the request.
